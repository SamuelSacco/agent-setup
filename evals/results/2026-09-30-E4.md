Claim: concrete tool failures land in the sidecar as structured events, in
both tools, without polluting the prompt.
Threshold: ≥4/5 induced failures produce a parseable JSONL event with
timestamp + kind, per tool.
Induced failures (identical in both tools): `python --version` (127),
`cat` of a missing file (1), unittest of a missing module (1), `json.tool`

## Claude Code — PASS (5/5), after an adapter fix

First run with the original adapter: **0/5 events**. Diagnosis: the adapter
mapped canonical `tool_failure` to Claude's `PostToolUse`, which fires only
on success — the only events recorded were 4 successful `Read` calls,
mislabeled `tool_failure`. Claude exposes failures on a separate event,
`PostToolUseFailure`.

Adapter fixed (`scripts/adapters.py`: `tool_failure` → `PostToolUseFailure`)
and retested: **5/5 parseable events**, each with UTC timestamp, kind
`tool_failure`, tool name, and the real error text
("command not found: python", "Expecting property name enclosed in double
quotes…"). Transcript: `2026-09-30-E4-claude-transcript.json`. Cost $0.0257.

This is the adapter layer earning its keep: the canonical concept was right,
the native mapping was wrong, and only a live failure test could show it.

## Addendum — re-test 2026-09-30 ~01:45 ET: mechanism corrected

The changelog audit (`hidden_files/research/2026-09-30-changelogs.md`)
contradicted the "no hook loader" attribution above: repo hooks exist
upstream since v1.0.49 but prompt mode gates them behind folder trust.
The original wording of this file (kept above for the record) also relied
on an earlier string search that the binary-forensics pass later
superseded — the loader machinery is in the bundle.

Re-test (fresh dir `/tmp/e4r`, `.github/hooks/test.json` with marker
hooks, BYOK Haiku, five short runs):

- Plain headless run and `GITHUB_COPILOT_PROMPT_MODE_REPO_HOOKS=1`:
  **0 markers** — hooks do not load untrusted. This reproduces the
  original 0/5 and explains it: the test ran untrusted, not hookless.
- `COPILOT_ALLOW_ALL=true` (the CLI's own `help environment` text: exact
  `"true"` "additionally trusts the working directory", which loads its
  hooks): **hooks fire**. `sessionStart`, `preToolUse`, `postToolUse`
  all produced markers.
- `postToolUseFailure` **never fired**, including for a bare
  `python --version` (exit 127). Payload capture shows why: the shell
  tool reports `"resultType":"success"` even on exit 127; the failure
  exists only in `toolResult.textResultForLlm`
  ("…completed with exit code 127"). At the tool layer, a failed shell
  command is a success.

Corrected Copilot verdict: hook surface **exists and fires when the
directory is trusted**; the documented failure event does not
discriminate shell failures on v1.0.89. Failure capture on Copilot =
`postToolUse` hook + parse the payload's exit-code text. That adapter is
identified, not yet built. (Whether `postToolUseFailure` fires for
non-shell tool classes is untested.)

S4's Copilot leg changes from REFUTED to PARTIAL-with-mechanism. The
earlier 0/5 observations in this file were accurate; the attribution was
wrong.
