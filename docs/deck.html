Team session · Agentic coding setups

One Setup, Two Agents

A tool-agnostic workspace for Claude Code and GitHub Copilot CLI: one place to define skills, agents, and MCP servers; one shared memory; and an evaluation habit that tells us whether any of it actually helps.

Sterile by design — nothing personal in it. Clone it, run one install command, and both tools behave the same.

The problem

Two agents, two configs, and knowledge that evaporates

  • Every capability gets configured twice — once per tool — then drifts.
  • What an agent learned in Monday's session is gone by Tuesday, and invisible to the other tool forever.
  • Most "agent setup" advice is folklore: claims copied from posts, never tested.

The fix is not a bigger config. It's a shared layer, a shared memory, and proof.

Shared memory

A root-level wiki the agents maintain themselves

Pattern after Andrej Karpathy's llm-wiki: immutable raw sources → LLM-maintained linked Markdown → a schema file that teaches maintenance.

  • Every note carries YAML frontmatter: id, type, status, verified date, relates_to links, superseded_by.
  • Lifecycle: active → stale → archived. Retirement is rule-based, not vibes: unverified >180 days and no inbound links, or a claim refuted.
  • index.md is the map; log.md is append-only. Git-backed, Obsidian-viewable.
Session lifecycle

Orient → log → harden

  • Orient: every session starts by reading the index, the data model, and the recent log.
  • Log: a session file records intent, then turn-by-turn: intended / tried / happened — failures included.
  • Harden: at the end, durable facts are distilled into wiki notes; the raw log stays untouched.

Both tools write the same format into the same directories. That's what makes "Claude started it, Copilot continues it" possible — demo, next.

Cross-tool continuity

One tool does a small task and hardens the wiki. We quit it, open the other tool cold, and ask: "What did the last session change, why, and what failed?"

It answers from the shared session log — in E2, Claude answered 5/5 probes from a Copilot session, including the trap question whose correct answer was "that decision is in no note." The no-wiki baseline answered "not recorded" 5/5 and invented nothing. Third act: an intentionally broken command lands as a structured event in the telemetry sidecar — data, not prompt noise.

Telemetry

Failures become data — outside the context window

  • Hooks capture concrete failures (wrong interpreter, failing tests, bad edits) as JSONL events in a sidecar store.
  • Only summaries re-enter the prompt. Rich telemetry never bloats context.
  • Storage decision: JSONL/SQLite, not Postgres — single writer, low volume, file-native consumers. Postgres earns its place with concurrent writers or cross-machine queries.
  • PROVEN Claude: 5/5 induced failures landed as events — after the adapter fix. First attempt mapped to PostToolUse (success-only) and captured nothing but successful Reads; failures live on PostToolUseFailure.
  • PARTIAL Copilot CLI v1.0.89: hooks are trust-gated — untrusted headless runs never load them (our first 0/5). Trusted (COPILOT_ALLOW_ALL=true): lifecycle hooks fire, but postToolUseFailure never fires for shell failures — the tool reports success and buries "exit code 127" in the result text. Capture = parse the payload. Adapter path identified, not built.

Tips & tricks — verified edition

Two second-opinion features, honestly priced

Claude Code /advisor PROVEN

  • Sonnet 5.5 drives; Opus 5.5 advises at decision points.
  • Cheaper than Opus-only — not free: each consult bills at Opus rates and re-reads the full transcript.
  • Short tasks: pure overhead. Anthropic's docs say so.

Copilot rubber duck PROVEN

  • Built-in critic on a different model family than your driver (Claude↔GPT) — no shared blind spots.
  • Manual by default: /rubber-duck when you ask. Auto-invoke exists but is opt-in (rubberDuckAutoInvoke, off by default). Read-only.
  • Costs extra model calls; the bet is early catches pay for them.
Myth check

"Opus 5.5 broke my old prompts"

UNVERIFIABLE as a general claim. No primary source or controlled study supports it — and the viral post behind the claim gets facts wrong (XML is not deprecated; the tool format didn't change).

  • Real: prefilled final-turn responses now error.
  • Real: leaving effort unset changes your token budget.
  • Reasonable: prompts forcing exhaustive visible step-by-step may show less surface reasoning.

That's retuning advice, not a regression. If a claim can't cite its test, it doesn't get repeated.

The setup, lightweight

Rules we actually run by

Heuristics, not theorems — each one is cheap to adopt and has a mechanism behind it:

  • Keep the tool surface ≤ ~35 tools per agent. Tool schemas cost context every turn (tonight: 23 schemas ≈ 7.7k input tokens). Past that, split the work into subagents with narrow surfaces instead of growing one agent's.
  • Budget the context you always pay. System prompt + tool schemas + orientation = the rent on every call. Measure it (1,866 vs 14,510 vs 20,589 — same probe), keep the system prompt lean, and move weight into on-demand context: skills and wiki pages load only when invoked.
  • Let telemetry close the loop. Both harnesses emit OpenTelemetry; capture to files, review what failed, and promote proven lessons into skills. The setup improves from its own evidence, not from vibes.
  • Notes have a lifecycle; forget on purpose. Active → stale → archived by rule (E5: −38% orientation tokens, nothing active-scope lost, nothing invented). Deprecation is a feature, not housekeeping.
  • Cleanup runs at close, not when remembered. A session-end hook invokes the cleanup skill automatically — session record written, wiki hardened, failures filed — so no session ends unlogged.

Each rule traces to a measurement or a failure in evals/results/. Where a rule is a judgment call rather than a proven claim, the ledger says UNVERIFIABLE and moves on.

Close

Evidence over enthusiasm

Agents are easy to demo and hard to trust. The setup is the small part — shared instructions, one-install capabilities, a maintained wiki, failures as data. The discipline is the product: every claim labeled, every eval pre-registered, every REFUTED kept on the record.
